# Credit-Card Fraud Detection - Is Balancing the Training Data Necessary?

A four-stage machine-learning pipeline on the Kaggle credit-card fraud dataset. Each stage is
one Jupyter notebook, and all four run end to end on Kaggle as chained kernels.

---

## 1. Project overview

Real credit-card fraud is rare - **0.58%** of transactions in the training file. That single
fact drives every design decision here, and the pipeline answers two research questions about
it, plus a diagnostic that came out of the first one.

| # | Question | Answered in |
|---|---|---|
| **RQ1** | Is it necessary or beneficial to balance the training data, or is training on the original imbalanced distribution preferable? | `04_evaluation.ipynb` - Analysis 1 |
| - | Are the resulting models overfitting, and why do balanced models behave differently? | `04_evaluation.ipynb` - Analysis 2 |
| **RQ2** | When fraud labels are available, do supervised classifiers outperform classic unsupervised anomaly detectors, and by what margin? | `04_evaluation.ipynb` - Analysis 3 |

Two rules hold across every experiment:

- **Balancing is a training-only choice.** The test set is never balanced, so the results
  reflect the real world, where fraud stays rare.
- **Accuracy is not the headline metric.** A model that answers "legitimate" for all 555,719
  test transactions scores 99.61% accuracy and catches nothing. Precision, Recall, F1 and
  **PR-AUC** carry the conclusions.

## 2. Dataset

- **Source:** [Kaggle - Credit Card Transactions Fraud Detection Dataset](https://www.kaggle.com/datasets/kartik2112/fraud-detection) (`kartik2112/fraud-detection`)
- **Files:** `fraudTrain.csv` (351 MB), `fraudTest.csv` (150 MB) - the official time-based split
- **Origin:** generated by the Sparkov simulator across 1,000 simulated cardholders and 800 merchants, so it contains no personal data
- **Columns:** 23 raw fields - timestamp, card number, merchant, category, amount, customer name/address/job, customer and merchant coordinates, `is_fraud`

| Split | Rows | Fraud rows | Fraud rate |
|---|---|---|---|
| `fraudTrain.csv` | 1,296,675 | 7,506 | 0.5789% |
| `fraudTest.csv` | 555,719 | 2,145 | 0.3860% |

Imbalance in training: **171.8 : 1**. There is no `trans_num` overlap between the two files,
so there is no row-level leakage.

### Engineered features (22)

| Feature | Why |
|---|---|
| `amt`, `log_amt` | Amount, plus a log transform because the distribution is heavily skewed |
| `age` | Derived from `dob` and the transaction timestamp |
| `hour`, `dayofweek`, `is_night` | Time-of-day and weekday patterns |
| `distance_km` | Haversine distance between customer and merchant coordinates |
| `gender` | Encoded binary |
| `city_pop` | City-size context |
| `category_*` (13 columns) | One-hot encoding of the 14 merchant categories |

Dropped: names, street, city, state, zip, occupation, card number, transaction ID, merchant
name, Unix timestamp and the raw coordinates - identifiers a flexible model could memorise
instead of generalising from.

## 4. The four notebooks

Each notebook has its own explanation file with a full walk-through - what it does, why it
does it that way, what it writes, and how to run it.

### [`01_data_loading.ipynb`](01_data_loading.ipynb) → [explanation](01_data_loading_explanation.md)

Loads both CSVs, inspects structure (`head`, `info`, `describe`, missing values, duplicates,
class counts), runs the train/test leakage check on `trans_num`, then builds the engineered
feature matrix with `haversine_km()` and `engineer_features()` and aligns train/test columns.

**Writes:** `output/data/train_fe.parquet`, `test_fe.parquet`, `train_eda.parquet`,
`output/results/data_validation.csv`

### [`02_eda.ipynb`](02_eda.ipynb) → [explanation](02_eda_explanation.md)

Class balance (count plot, bar + pie), transaction amount by class (box plot, capped density
histogram, `groupby.describe`), fraud rate by hour of day, fraud rate by merchant category,
and a check of two engineered features against the target.

**Writes:** `output/plots/01`–`06`, three EDA tables

### [`03_model_training.ipynb`](03_model_training.ipynb) → [explanation](03_model_training_explanation.md)

Builds `X`/`y`, fits a `StandardScaler` on the training features only, constructs the balanced
training set by Random Under-Sampling (all 7,506 frauds + 7,506 sampled legitimate rows), and
fits seven models:

| Group | Training data | Models |
|---|---|---|
| A. Imbalanced | Full train, 1,296,675 rows | Logistic Regression, Random Forest |
| B. Balanced | Under-sampled 1:1, 15,012 rows | Logistic Regression, Random Forest |
| C. Unsupervised | Legitimate rows only, no labels used | Isolation Forest, One-Class SVM, Local Outlier Factor |

No scoring happens here - predictions and anomaly scores are stored so that stage 4 is pure
evaluation.

**Writes:** `output/models/*`, `output/preds/*`, `output/plots/07`

### [`04_evaluation.ipynb`](04_evaluation.ipynb) → [explanation](04_evaluation_explanation.md)

Reads the stored predictions and produces all three analyses: imbalanced vs balanced
(metric table, bar chart, ROC and PR curves, confusion matrices, feature importance), the
overfitting diagnostic (train vs test with explicit gaps), and supervised vs unsupervised.
Written conclusions sit in markdown cells beside the numbers.

**Writes:** `output/plots/08`-`17`, four metric tables

The dependency graph is `01 → {02, 03} → 04`, where only 03 feeds 04. **Notebooks 02 and 03
can run at the same time**, and 02 can be skipped entirely without breaking the modelling
chain.

Each stage writes into `output/` and the next stage reads from it, through one helper:

```python
def upstream(rel):
    """Locate a file written by an earlier notebook (local run or Kaggle kernel input)."""
    local = OUT / rel
    if local.exists():
        return local
    if KAGGLE_IN.exists():
        for p in sorted(KAGGLE_IN.rglob(rel.split("/")[-1])):
            if p.as_posix().endswith("output/" + rel):
                return p
    raise FileNotFoundError("Run the earlier notebook first - missing: " + rel)
```

Locally all four notebooks share one `output/` folder, so the local copy is found first. On
Kaggle each notebook is a separate kernel and an upstream kernel's output is mounted under
`/kaggle/input/`, so the same line of code finds it there. Running a stage out of order gives a
clear error naming the missing file.

## 8. Headline results

Every model scored on the same untouched imbalanced test set - 555,719 rows, 0.386% fraud.

| Model | Precision | Recall | F1 | ROC-AUC | PR-AUC |
|---|---|---|---|---|---|
| Imbalanced · Logistic Regression | 0.7778 | 0.2186 | 0.3413 | 0.8619 | 0.3463 |
| **Imbalanced · Random Forest** | **0.9426** | 0.7506 | **0.8357** | 0.9961 | **0.8819** |
| Balanced · Logistic Regression | 0.0303 | 0.8233 | 0.0585 | 0.9514 | 0.1633 |
| Balanced · Random Forest | 0.1506 | **0.9716** | 0.2608 | 0.9968 | 0.8014 |
| Unsupervised · Isolation Forest | 0.1890 | 0.3445 | 0.2441 | 0.8612 | 0.1052 |
| Unsupervised · One-Class SVM | 0.0923 | 0.3193 | 0.1432 | 0.8270 | 0.0567 |
| Unsupervised · Local Outlier Factor | 0.1606 | 0.2531 | 0.1965 | 0.8878 | 0.1159 |

### In operational terms

| | Imbalanced RF | Balanced RF |
|---|---|---|
| Frauds caught | 1,610 | 2,084 |
| Frauds missed | 535 | 61 |
| False alarms | 98 | 11,754 |
| Alerts raised | 1,708 | 13,838 |
| **Reviews per fraud found** | **1.1** | **6.6** |

### Conclusions

**Random Forest on the original imbalanced data is the best model in the project** -
precision 0.94, recall 0.75, F1 0.84, PR-AUC 0.88. It catches three-quarters of fraud while
raising only 98 false alarms across 555,719 transactions.

**Balancing is not automatically an improvement.** It reliably raises recall and reliably costs
precision: 474 more frauds caught, at **25.6 extra manual reviews per extra fraud**. It is the
right choice only when catch-rate explicitly outweighs review cost.

**The balanced model's weakness is prior mismatch, not overfitting.** Its recall barely moves
from train to test (0.9923 → 0.9716), so nothing was memorised; what collapses is precision
(0.9936 → 0.1506), because it learned that fraud is common while the test world keeps it rare.
The fix is a threshold adjustment, not retraining.

**Labels are worth a great deal.** The best supervised PR-AUC (0.8819) is **7.6×** the best
unsupervised one (0.1159). Anomaly detectors flag what is unusual, which is not the same as
fraudulent - rare but legitimate large purchases look identical to them.

**Accuracy is the wrong metric here, consistently.** Every model in the table scores above 0.89
accuracy, including one that raises 56,454 false alarms.

## 9. Limitations

- **Synthetic dataset.** Figures are an upper bound on real-world performance, not a deployment guarantee.
- **One balancing ratio.** Only 1:1 was tested; intermediate ratios and SMOTE were not.
- **No threshold sweep.** All models are compared at the default 0.5 cut-off. Since the balanced model's problem is a threshold problem, a cost-optimal threshold search is the obvious next step.
- **Balancing is confounded with training-set size.** The balanced arm trains on 15,012 rows against 1,296,675 - 86× less data. Control arms (`class_weight="balanced"` on full data, and a random 15,012-row imbalanced subsample) would separate the two effects.
- **Two unsupervised detectors subsampled.** One-Class SVM and LOF were fitted on 40,000 legitimate rows because both scale quadratically.
- **Single train/test split.** No confidence intervals.
- **`is_night` window.** Defined as hours 0-5, it excludes the two highest-fraud hours (22:00 at 2.88%, 23:00 at 2.84%) and includes two baseline ones. It ranks 10th of 22 features; the raw `hour` feature ranks 3rd and carries the time signal instead. See [`01_data_loading_explanation.md`](01_data_loading_explanation.md#10-a-limitation-worth-knowing).

## 10. Reproducibility

A single fixed random seed (`RANDOM_STATE = 42`) is used at every stochastic step: the
under-sampling draw, the shuffle, both Random Forests, the Isolation Forest, and the 40,000-row
and 100,000-row subsamples. Re-running any notebook reproduces its numbers exactly.

The scaler is fitted on training data only and reused for the balanced set, so no test
statistic ever reaches a training pipeline.

**Dependencies** (`requirements.txt`): numpy, pandas, matplotlib, seaborn, scikit-learn,
ipykernel, jupyter, pyarrow, joblib.
